# Native Photon reply-target feasibility — staging investigation

**Status:** feasibility supported by pinned-source tracing and synthetic probes; live Photon behavior unverified. This is neither Task A implementation nor authority to file a Gateway request. Investigated 2026-10-14. Production files were read only.

## Pinned path and result

The installed sidecar uses `@photon-ai/advanced-imessage` 2.1.0 and `@spectrum-ts/imessage` 12.7.0 (`/home/alfred/.hermes/hermes-agent/plugins/platforms/photon/sidecar/package-lock.json:479-480,619-620`). The native SDK message has **separate** optional `replyTargetGuid` and `threadOriginatorGuid` fields and a mandatory `isForward` field (`.../@photon-ai/advanced-imessage/dist/groups-CMgks3Ll.d.ts:429,442-449`). Its protobuf mapper copies those native fields independently (`.../dist/chunk-KA2VVWQX.js:6711-6759`). The protobuf also has `replyToGuid` (`.../dist/chunk-KA2VVWQX.js:2385-2388,2502-2512`), but the public `mapMessage` output does **not** surface that separate field. Its provider semantics are unknown here.

Spectrum receives the full native message and builds a base record using `toMessageMetadata` (`.../@spectrum-ts/imessage/dist/index.js:1004-1036,1070-1083,1258-1270`). The installed metadata schema and mapper omit all three native provenance fields (`:382-405,1004-1036`). Spectrum instead computes `message.replyTargetGuid ?? message.threadOriginatorGuid` (`:1173`), resolves an older target from cache or SDK, and substitutes a stub if lookup fails (`:1182-1209`). The resulting `content.target.id` cannot say whether the inbound event directly targeted that message or merely inherited a thread origin; target hydration and `target.direction` are also fallible. Spectrum core parses metadata through the platform schema and spreads it onto the resulting `Message` (`.../@spectrum-ts/core/dist/index.js:2453-2489,2740-2797`). Therefore merely adding a field to a sidecar JSON object would not recover information already dropped by Spectrum.

The installed sidecar's reply normalization emits `targetMessageId: target?.id` and `targetDirection` (`/home/alfred/.hermes/hermes-agent/plugins/platforms/photon/sidecar/index.mjs:575-590`). `normalizeEvent` forwards that normalized content, a message ID and `sender.id`, not the direct native field (`:642-659`). Its only `app.messages` consumer forwards to ordinary Hermes and marks read after the forward (`:701-715`). The Hermes adapter uses `targetMessageId` for conversation context and may use its sent-message cache to infer a target was its own (`/home/alfred/.hermes/hermes-agent/plugins/platforms/photon/adapter.py:827-854`). It also substitutes a missing `sender.id` with the space phone or space ID (`:829`). These are presentation/conversation conveniences, **never** proof of an authenticated owner confirmation.

For a protected preview sent as plain text, Spectrum returns the SDK send result's `message.guid` as its outbound record ID (`.../@spectrum-ts/imessage/dist/index.js:1704-1710,1738,1772-1780`). The sidecar `/send` route returns that record's `id` as `messageId`, or `null` if absent (`.../sidecar/index.mjs:1067-1089`). The gate must durably record a nonempty actual send ID before arming a challenge. An unknown send result or crash between send and durable record leaves an unarmed preview; a later reply cannot authorize it. This local source path does not prove that the provider preserves the same ID as a reply target across devices, delays or reconnects.

**Feasibility conclusion:** the existing lower-level SDK carries direct-target provenance on the *same* connection, but the installed Spectrum/sidecar/Hermes interface does not expose it. A small Spectrum metadata change can pass it to the protected sidecar within its existing iterator. No second Photon connection is needed by this source design. Only an isolated live test can confirm provider semantics and operational reliability.

## Proposed minimal upstream change

[`patches/spectrum-native-reply-provenance.proposed.patch`](patches/spectrum-native-reply-provenance.proposed.patch) adds optional `nativeReplyTargetGuid`, `nativeThreadOriginatorGuid` and `nativeIsForward` to the pinned Spectrum metadata schema, mapper and declarations. It intentionally leaves the ordinary combined `content.target` behavior intact. The patch applies to a disposable copy of the pinned compiled package and `git apply --check` succeeds against the installed source; it has **not** been installed. The missing schema comma found during live-test readiness review was corrected; the full patched module now parses and imports with pinned dependencies (`NATIVE_REPLY_PATCH_VERIFICATION.md`). A maintained upstream source release must regenerate compiled JavaScript, declarations and source maps. The protected sidecar would then read these fields from the SDK-originated `Message` **before** sending a derived ordinary event to Hermes. The patch itself creates no private gate, socket or authorization path.

The native SDK's omitted `replyToGuid` is not used as confirmation proof. Before implementation, a maintainer should examine upstream native source and live captures to decide whether `replyTargetGuid` is in fact the direct per-message target on the deployed provider. If `replyTargetGuid` is absent or rewrites to a thread origin in valid direct replies, this candidate criterion fails; never substitute `threadOriginatorGuid`, the Spectrum content target or a Hermes cache.

## Confirmation boundary required after authorization

1. The protected owner observes inbound SDK events on the one existing iterator and records explicit native sender address, authenticated account/project, direction, DM conversation, immutable event ID/text, direct target, thread origin, forward flag and observation health. Missing or conflicting fields fail closed. A Hermes or model supplied copy cannot create provenance.
2. The protected owner sends the complete canonical draft preview, durably records its actual returned outbound ID, exact draft digest/version, original event reference, account/owner/conversation and expiry, then arms that one challenge. An empty/uncertain ID is never armed.
3. A *fresh* inbound owner event must have a nonempty **native direct** `replyTargetGuid` equal to exactly one live preview ID, the expected owner/account/conversation and deterministic affirmative text. A generic yes, quoted text, forwarded message, `threadOriginatorGuid`, hydrated/stub target, `targetMessageId`, Hermes session, current handle or model assertion is insufficient. Changed scope, missing/duplicate ID, conflict, expiry, replay and reconnect uncertainty revoke or reissue the challenge.
4. A confirmation authorizes only one immutable `alfred.devreq/1` submission to the statically bound requester inbox. The Gateway alone files a canonical `proposed` task. It does not approve execution or any GitHub action.

The current sidecar gives a holder of its shared token `/shutdown` and arbitrary-path `/send-attachment` access (`.../sidecar/index.mjs:1006-1033,1061-1064,1100-1132`). Current Hermes knows the ordinary sidecar token and uses its routes. Any authorized implementation must first separate privileged control, credentials and private observation from Hermes at the whole-process boundary described in proposed ADR 0009. Adding a direct-target field to ordinary Hermes events, or trusting it from Hermes IPC, would not satisfy the design.

## Compatibility and decisions

This narrow patch is consistent with the *proposed* natural-language confirmation gate in `design-v1/ADR_0003_AMENDMENT_PROPOSED.md:11-31`, the proposed protected whole-process placement in `design-v1/ADR_0009_LINUX_EXCEPTION_PROPOSED.md:13-35`, and `design-v1/TASK_A_REVISED_STAGING_SPEC.md:19-50`. It keeps ordinary Spectrum reply normalization and the one sidecar connection. It does not make those ADRs authoritative, resolve the current powerful sidecar routes, certify ordinary media/Evidence Bridge compatibility, or waive proposed ADR 0011's Gateway task-ID safety gate.

The immediate next step is the separately approved isolated live test in [`NATIVE_PHOTON_ISOLATED_LIVE_TEST.md`](NATIVE_PHOTON_ISOLATED_LIVE_TEST.md). Implementation would additionally require human adoption of revised ADR 0003 and the ADR 0009 exception, a canonical ready Task A spec with exact reviewed SDK/sidecar/service/permission diffs and rollback, independent OS isolation acceptance, and separate authorization before any real Gateway filing. Task B, CTO scheduling, execution and GitHub permissions remain separate decisions.
