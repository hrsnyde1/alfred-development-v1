# Photon Task A threat model — v0.1.4 corrective staging

## Updated unresolved paths

- Spectrum's stream cursor is held in memory and the installed implementation
  explicitly accepts a gap after cursor rejection. A crash before the
  sidecar's first fsync may permanently lose an event. Real observations are
  durably held with `continuity=unverified`; Hermes delivery and Gateway filing
  fail closed. There is no provider-backed or authorized manual reconciliation
  procedure yet.
- A per-job adapter context prevents the previous handle from leaking into a
  normal queued drain, but the installed Gateway can merge or discard same-chat
  pending text. An untrusted Hermes caller can choose another live handle it
  already possesses. The protected front can prove that the handle came from
  an authenticated event and that the destination matches that event; it cannot
  prove that arbitrary outbound text was generated by that exact processing
  turn. Full event-to-turn integrity is therefore unresolved.
- Inbox publication now uses `RENAME_NOREPLACE` and resynchronizes an existing
  final file before marking the ledger sent. Pre-rename orphan temporary files
  require Gateway-side cleanup in a future reviewed procedure. The broker
  retains search/write only access to the inbox.
- Every handled authorization denial is written as a code-only audit record
  until the 4 MiB budget is reached, at which point the protected operation
  fails closed. SDK/OTel diagnostic privacy and operator rotation remain
  unverified.

## Historical v0.1.3 model

This is a staging design for the isolated `dev-001` lab. The protected Photon
identity owns the only Spectrum connection, project credentials, private
sidecar socket, event spool, journal, and lab inbox writer. Hermes is an
untrusted caller of the restricted Unix socket. The lab Gateway alone parses
and files canonical `alfred.devreq/1` envelopes. No Task B authority exists.

## Assets and attacker capabilities

An attacker controlling Hermes prompts, tools, plugins, or its Unix socket
requests may choose text, paths, recipient strings, envelope fields and call
timing. The attacker may open many stalled connections and replay previously
seen handles. They must not be able to read Photon credentials, private SDK
events, unrelated inbox entries, or Gateway state, nor send to an unapproved
destination or stop the sidecar. A compromised protected Photon UID is outside
this isolation boundary and must be treated as a full intake compromise.

## Controls proposed in v0.1.3

- Systemd owns the restricted socket (`alfredphoton:alfredhermes`, `0660`);
  the protected runtime directory is `0751`. The private sidecar socket is
  `0600`, under the protected UID. Both interfaces check kernel peer UID.
  LoadCredential files and the single child process are confined to the
  protected service. `task_a/service.py` supervises launch, health, restart
  and termination. Node stdout/stderr are discarded because SDK diagnostics
  are not proven privacy-safe; the broker writes bounded code-only audit.
- The sidecar fsyncs an owner-only spool record and directory before sending
  an event. The broker fsyncs its owner-only journal before acknowledging the
  sidecar. The sidecar marks a live SDK message read only after acceptance.
  Unavailable admission leaves the spool record pending; explicit policy
  rejection removes it without a read receipt. Oversized and normalization
  failures become durable content-free rejection records. A spool write
  failure terminates the sidecar for supervised recovery.
- Each journal record has a random handle, explicit sender, destination,
  message and time. The adapter uses task context for the exact inbound turn;
  no latest-handle-per-chat map remains. Legacy message deduplication is
  disabled in Task A mode so journal retries reach Hermes. A reply reserves
  its handle durably before external send. Uncertain sends cannot retry under
  the same handle. A failed turn may replay at most three times in one broker
  lifetime; delayed work is audited and remains on disk for restart recovery.
- The restricted API has bounded text replies and canonical lab submissions
  only. Attachment paths and private control routes are absent from Hermes.
  The inbox is search/write-only to the broker through `O_PATH`, while the
  setgid directory and `0640` files provide Gateway group read. Publication
  used no-clobber hard-link commit, file fsync and filesystem sync.
- The HTTP listener caps concurrent handlers at 32, backlog at 32 and POST
  request lifetime at five seconds. Its event queue and persistent journal
  each cap at 1,024 entries. Audit storage caps at 4 MiB and fails closed.

## Residual and independent acceptance risks

The installed Photon SDK may treat an iterator yield as acknowledgement even
if the sidecar crashes before its spool fsync. Its replay and read-receipt
semantics need live verification with a disposable account. Cross-UID DAC,
systemd directory ownership, group inheritance, socket activation and
service mount restrictions need separate Linux testing. Node or broker code
compromise under the protected UID can access protected state and the lab
inbox. Operator rotation of the bounded audit log must be designed before
production. The broad legacy Hermes Photon regressions did not complete in
this sandbox; their media assumptions require explicit compatibility review.

## Team skills for Developer specialists (handoff.12)

Skill text reaches a Developer model prompt, so it is treated as instructions with
the owner's authority. Threats and controls:

- **A proposer (Lucius Fox) or a compromised Fox token adds a harmful skill.** Fox can
  only open pull requests; the owner merges. Delivery needs the owner, as root, to name
  a merged commit; the deploy tool refuses commits not on `main`.
- **An alfred-UID process edits the library checkout or a delivered skill.** Root reads
  only its own `transfer.fsckObjects` clone; snapshots are root-owned and not group or
  world writable; the loader checks owner, mode, link count, an exact file list and
  every SHA-256 on each load.
- **A library change loosens the rules.** The format, safety-screen and budget rules are
  copied into the hash-pinned `developer_v1/team_skills.py` and re-run at load; a test
  fails if they drift from the library validator.
- **Skills change between approval and execution.** The plan records commit, id and
  SHA-256 per skill; the development grant binds the plan digest; the Developer reloads
  the plan's commit, not `ACTIVE`, and refuses any difference before claiming the grant.
- **A skill tries to widen authority.** The payload states that team practices never
  permit other files, commands or scope, and nothing relies on that sentence: the edit
  contract, scoped paths, isolated applier and approved checks are unchanged.
- **Prompt size.** Team practices are capped at 24 KiB and the role budget.

Residual: a skill can still steer *how* an approved change is written within scope;
the owner's review at merge time and independent QA and Review remain the controls.
