## ADR 0003 Phase 4: proposed limited authorization

Authorize a controlled Phase 4 intake pilot for **one authenticated owner**, company `alfred`, project `dev-001`, and one pending request. Personal Alfred may identify a natural-language development request and draft the existing `alfred.devreq/1` fields. The existing single Photon connection remains the messaging interface. A separately protected gate may send a full bounded preview to the original owner DM and may publish the exact frozen envelope to the statically bound Hermes inbox **only** after it observes a fresh original Photon SDK event from that owner, with a native direct reply target equal to the preview's outbound ID, explicit non-forwarded state, affirmative text and an unexpired challenge. Hermes event IDs, digests, session context and model assertions alone grant no filing authority. Ambiguous or lost delivery fails closed and requires a fresh request. The trusted Gateway alone resolves the protected registry and creates one canonical `proposed` task. The confirmation grants submission only; the existing human approval, hash binding, PAUSE/STOP, protected execution, GitHub publication, merge and deployment gates remain unchanged. No CTO scheduler, developer run, or second Photon connection is authorized by this amendment.

Before first real pickup, approve the exact `dev-001` registry row and path, the V1.1a allocation correction, the V1.1b intake install, the one-request acceptance test and rollback. The decision must explicitly lift the existing hold on `gateway.py run-once` **for this isolated lab target only** after the task-ID safety work is accepted. Do not infer that accepting ADR 0011 alone installs a fix.

## ADR 0009: proposed narrow requester-permission change

Keep `hermes` as the sole statically bound requester. For the controlled V1.1 pilot only, permit the existing `local` terminal backend when Hermes and all its in-process tools and terminal children run as the dedicated `alfredmsg` UID inside the reviewed systemd whole-process boundary. That boundary must deny reading or writing the protected Gateway checkout, registry, journal, approval state, Photon project credentials, sidecar control token and direct inbox, and deny writing the task repository, while allowing a private writable workspace under `/var/lib/alfredmsg/hermes`. Give Hermes only the reviewed Unix intake client socket, ordinary sidecar messaging token and restricted media spool. A protected gate with a **different UID** is the sole writer of `~/Alfred/projects/hermes-requests/inbox`; the Gateway retains read/pickup authority and stamps `source: hermes` from that same bound folder. The Photon sidecar uses a third UID, retains the existing single connection and supplies original SDK observations to the gate. Confirm UID, group, mount, socket and inbox permissions on the host before activation. Preserve the Evidence Bridge and read-only status tools.

This is a **proposed narrow exception** to the accepted ADR 0009 Docker-only terminal rule. It grants ordinary Personal Alfred terminal use within the `alfredmsg` process boundary, but no protected development execution, approval, GitHub or Gateway authority. It does not change the envelope schema, create a new requester identity or authorize any other company or repository. Do not add `alfredmsg` to the rootful `docker` group or expose `/var/run/docker.sock`.

The inspected Ubuntu Hermes config currently has both `terminal.backend: local` and `TERMINAL_ENV=local`. Keep both values in the new sanitized Hermes home/unit and leave the old home and user unit unchanged for rollback. The proposed exception requires host proof that a terminal command runs as `alfredmsg`, can write its private workspace, and cannot read or write protected Gateway paths from inside the actual Hermes service boundary. Until this amendment is accepted and those checks pass, the current working Hermes service remains the terminal provider.
